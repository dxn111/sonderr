## Workflow
1. Start from the actual diff, issue list, and verification output—not memory or intent.
2. Group changes by user outcome: new capability, improvement, fix, security/privacy, and known limitation.
3. State upgrades, migrations, compatibility impact, and rollback facts when they exist.
4. Avoid promises such as fully secure, unbypassable, or guaranteed. Describe concrete boundaries instead.
5. Include a short verification section with commands or manual paths that were actually run.

## Verify
- Every claim maps to a committed change or test result.
- Security notes do not reveal exploitable details before a coordinated fix.
- A user can tell whether they need to take action after upgrading.
