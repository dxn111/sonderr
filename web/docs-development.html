Sonderr Developer Program

Help make Sonderr more useful, understandable, and dependable. Contributions can improve the local workspace, engineering tools, skills, docs, design, testing, or safety boundaries. Focused work with clear evidence is easiest to review.

Who can contribute

Developers, designers, writers, testers, translators, and security-minded reviewers are welcome. You do not need to be a professional contributor; explain what you tried and where you got stuck.

What the program offers

A place to improve the project, receive maintainer feedback when capacity allows, and have accepted work credited in the project history. No response time or acceptance is guaranteed.

Contribution tracks

Engineering

Workspace tools, provider behavior, file handling, reliability, install flow, and clear error recovery.

Skills and prompts

Handwritten task playbooks, long-task continuity, better tool selection, evaluation cases, and grounded responses.

Design and accessibility

Composer and settings clarity, keyboard use, responsive layouts, accessible labels, and useful empty/error states.

Docs and onboarding

Accurate setup steps, examples that work, current feature descriptions, troubleshooting, and translations.

Testing and reliability

Reproducible bugs, regression coverage, install checks, provider edge cases, and recovery from interrupted tasks.

Privacy and safety

Permission boundaries, safe diagnostics, secret handling, prompt-injection resistance, and transparent external actions.

How to contribute

  1. Choose one user problem or a focused improvement.
  2. Check the current code and docs, then agree on a small finish line.
  3. Make the change in a branch and include tests or a reproducible explanation.
  4. Run the checks that apply and inspect the final diff for unrelated changes or sensitive data.
  5. Open a pull request when repository access is available, or ask in Discord where to start.

Local setup and checks

Use Node.js 20 or newer. From the repository root:

npm cinpm run checknpm test

In your handoff, say exactly which checks passed, failed, or could not run. Do not claim a manual check you did not perform.

Review principles

  • One change should solve one clear user problem and preserve unrelated work.
  • Security or privacy changes should explain the trust boundary and test both allowed and denied paths.
  • Skills should give concrete steps, limits, failure handling, and a way to verify the result.
  • Do not commit credentials, private user data, real wallet keys, or live account exports. Use fixtures, mocks, or test networks.
  • Hidden telemetry, unexpected network calls, broadened permissions, and silent external actions need a clear user benefit and explicit review.

Program boundaries

The Developer Program is a volunteer contribution path, not employment, a contract, or a promise of payment. The security bounty is a separate program for eligible, responsibly disclosed vulnerabilities; ordinary features and pull requests are not bounty claims. Sonderr is maintained by one solo developer, so review timing depends on capacity.

For a sensitive vulnerability report, use the private instructions on the Sonderr Bounty Program page. Do not post exploit details publicly before the maintainer has had a chance to respond.
