01 · Overview

What Sonderr is

Sonderr is a privacy-first local AI workspace. It helps you inspect a project, plan work, use configured model providers, and run workspace tools only through the access level you choose. Web3 features are optional capabilities for people who want them—not Sonderr’s whole identity.

What it can do

  • Explain project structure and relevant files.
  • Draft implementation plans and code.
  • Use workspace tools when permission allows.
  • Offer optional Web3 wallet visibility and review-first transaction tools.
  • Show tool activity and report failures.

What it cannot promise

  • Perfect answers, complete context, or secure code by default.
  • That a command ran unless it has evidence.
  • That a provider, model, or generated change is always safe.
  • That safeguards catch every harmful request.

02 · Privacy

Local data and provider requests

Sonderr is designed to keep control on your machine. You choose when a model provider receives a task and which local tools are available.

Stored locally

Workspace sessions, settings, enabled skills, and provider keys are stored locally. Keys are not displayed back in the interface.

Sent to a provider

When you configure a provider and send a task, the task and any context you attach may be sent to that provider. Review its own privacy terms.

Minimize sensitive data

Do not paste passwords, private keys, tokens, personal identifiers, or confidential files into a task unless you understand the destination and need.

Permissions are yours

Ask, auto-approve, full workspace, and full PC access have different risk. Use the narrowest setting that lets you finish the task.

03 · Safety

Safety boundaries

Sonderr should refuse requests that enable serious harm and should not turn a refusal into a workaround.

  • It must not help create, obtain, or distribute child sexual abuse material.
  • It must not help build weapons or explosives, enable violence, or facilitate serious wrongdoing.
  • It should protect credentials, avoid silent changes, and distinguish suggestions from actions it actually performed.
  • No automated safeguard is perfect. If unsafe content gets through, stop using it, preserve only safe diagnostic details, and report it.
For immediate danger, contact local emergency services. Do not upload illegal material or sensitive victim data to a public issue tracker.

03A · Experimental wallet

Sonderr Wallet is not a primary wallet

Sonderr can generate a local wallet and, after explicit confirmation, send supported assets. That does not make it a bank, custodian, exchange, audited hardware wallet, or guaranteed-safe vault.

Protect your money

  • Use it as an experimental or low-value testing wallet, not as your main savings wallet.
  • For your own security and money preservation, keep no more than €100 total (or equivalent) in it while the feature is experimental. This is a strong recommendation, not a technical limit.
  • Assume a bug, compromised dependency, wrong contract, malicious token, RPC failure, or user mistake could permanently lose funds. Blockchain transfers cannot be reversed by Sonderr.
  • Back up the encrypted wallet locally, keep the password separate, and never put a seed phrase or private key in chat, an issue, email, or a normal text file.
  • Every send must show the chain, asset, recipient, amount, calldata/instructions, and estimated fee before the user presses Confirm & send.
Only fund a wallet with money you can afford to lose. Price data and portfolio totals are estimates; they are not financial advice or a guarantee of solvency.

04 · Security research

Sonderr Bounty Program

Sonderr is maintained by a solo developer. Responsible security and safety research is welcome when it helps make the project safer for everyone.

What is in scope

  • Ways to bypass tool permission boundaries or execute a tool without the configured approval.
  • Secret or credential exposure caused by Sonderr itself.
  • Local path traversal, unsafe workspace access, or unintended privilege expansion.
  • Prompt or tool flows that reliably produce prohibited harmful assistance despite the stated boundaries.
  • Documentation or UI behavior that falsely claims an action occurred or hides material risk.

Out of scope

  • Issues only in a third-party provider, browser, operating system, or dependency without a Sonderr-specific impact.
  • Spam, social engineering, denial-of-service, physical attacks, or attempts to access another person’s data.
  • Reports based only on model quality, harmless refusals, or unsupported configurations.
€5–€10Typical small discretionary bounty for a clear, valid report. Higher or lower outcomes are possible and never automatic.

Do not exploit real users, access data you do not own, download illegal material, or publish a vulnerability before coordinating with the maintainer.

05 · Contributions

Sonderr Developer Program

Contributions are welcome across code, docs, UI, testing, skills, and safety review.

Good contributions

  • Focused fixes with a clear user outcome.
  • Regression tests and reproducible bug reports.
  • Accessible, responsive UI improvements.
  • Provider, tool, skill, and documentation improvements.

Before opening a PR

  • Explain the behavior change and affected files.
  • Run npm run check and relevant manual checks.
  • Keep secrets, personal data, and generated credentials out of commits.
  • Call out security, permission, or compatibility impact.

Maintainer expectations

Be direct, respectful, and specific. Small coherent changes are easier to review. A contribution may be declined when it expands permissions, weakens safety boundaries, or adds hidden network behavior without a clear user-facing reason.

06 · Reporting

How to report a bug or safety issue

  1. Check whether the issue is already known.
  2. Write a precise title and include the Sonderr version, OS, provider mode, and relevant access level.
  3. Describe expected behavior versus observed behavior.
  4. Include a short, sanitized proof of concept and reproduction steps. Redact keys, personal data, illegal material, and real victim information.
  5. For privacy, DM Dani through Discord or X. If you cannot reach Discord, use X to ask for the current private contact path.
  6. Give the maintainer reasonable time to investigate and fix the issue before public disclosure.

A valid, responsibly disclosed report with a clear PoC may receive a small discretionary €5–€10 bounty based on impact and report quality. Payout is not guaranteed, and the maintainer may decline reports that are unsafe, duplicative, out of scope, or missing enough detail to reproduce.

This handbook describes product behavior and project expectations. It is not legal advice or a substitute for a formal privacy policy, security policy, or emergency reporting channel where one is required.
